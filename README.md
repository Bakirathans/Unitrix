# Business Entity Resolution — Amazon ML Challenge 2026

An enterprise-grade, reproducible entity resolution system designed to resolve canonical business entities from Source 1 against large-scale, noisy candidate records in Source 2 and Source 3.

---

## 1. Problem Understanding
The task is Business Entity Resolution (Record Linkage) under the **Macro-averaged $F_{0.5}$ metric**:
$$F_{0.5} = \frac{(1 + 0.5^2) \cdot \text{Precision} \cdot \text{Recall}}{0.5^2 \cdot \text{Precision} + \text{Recall}} = \frac{1.25 \cdot \text{Precision} \cdot \text{Recall}}{0.25 \cdot \text{Precision} + \text{Recall}}$$

### Key Problem Nuances:
- **Precision-Biased Metric**: $F_{0.5}$ weights precision twice as heavily as recall. False positives severely degrade macro $F_{0.5}$, penalizing aggressive matching.
- **Heterogeneous Sources**: Source 1 contains canonical business entities, while Source 2 and Source 3 contain noisy, unstandardized records with missing addresses, legal entity suffix variations, typos, transliterations, and multi-tenant homonyms.
- **Cardinality Flexibility**: A Source 1 entity may match zero records (singleton), exactly one record, or multiple records across Source 2 and Source 3.
- **Scale**: The test set contains **1,732,544 Source 1 entities** and **9,969,589 candidate records** (4.89M Source 2 + 5.08M Source 3), requiring high-throughput multi-pass blocking and efficient vectorized inference.

## 3. Data Preprocessing
- **Field Preservation**: Raw fields (`business_name`, `business_address`, `country`) are preserved without destructive in-place mutations.
- **Country Handling**: Open-set country normalization converts missing/invalid tokens (`NaN`, `NULL`, `<MISSING>`) to a fallback `"GLOBAL"` key while preserving true country codes.
- **Whitespace & Encoding**: Strips trailing control characters and standardizes UTF-8 encoding.

---

## 4. Normalization
Implemented in `04_normalization.py`:
1. **Punctuation & Case**: Lowercasing and Unicode alphanumeric regex cleaning.
2. **Legal Suffix Stripping**: Strips enterprise/corporate entity designators (`inc`, `llc`, `ltd`, `corp`, `pvt ltd`, `gmbh`, `sa`, `bv`, `co`, `holdings`, `enterprises`).
3. **Address Standardization**: Maps abbreviations (`st` $\to$ `street`, `rd` $\to$ `road`, `ave` $\to$ `avenue`, `ste` $\to$ `suite`, `fl` $\to$ `floor`, `bldg` $\to$ `building`, `pkwy` $\to$ `parkway`).
4. **Alphanumeric Compaction**: Strips all non-alphanumerics for robust typo and spacing comparison.
5. **Domain Parsing**: Extracts clean root domain tokens from URLs/emails.

---

## 5. Blocking Strategy
Implemented in `05_blocking.py` and `14_test_inference.py`:
- **Multi-Pass Union Inverted Index**:
  1. `Pass 1: Alphanumeric Name (len >= 4)`: High-precision exact string matching.
  2. `Pass 2: Prefix Matching (6 & 8 chars)`: Handles suffix variations and trailing descriptors.
  3. `Pass 3: Distinct Informative Name Tokens`: Token-level inverted index excluding generic stopwords (`group`, `solutions`, `services`).
  4. `Pass 4: Two-Token Bigrams`: Captures compound business names (`t0_t1`).
  5. `Pass 5: Domain Matching (6 chars)`: Identifies businesses sharing domain stems.
  6. `Pass 6: Street Number + First Non-Stopword Address Token`: Resolves distinct name variants sharing exact physical locations.
- **Bucket Size Pruning**: Caps bucket size at `MAX_BUCKET_SIZE = 300` and retrieves top 15 candidate records per Source 1 entity, preventing generic token bloat.

---

## 6. Candidate Recall Measurement
Evaluated in `06_evaluate_blocking.py` on training ground truth:
- **True Match Candidate Recall**: **96.42%** of all true matches retained in the candidate pool.
- **Search Space Reduction**: Slashes candidate pairs from $1.73\text{M} \times 9.97\text{M} \approx 1.7 \times 10^{13}$ pairs down to **23.13 million pairs** (a **99.99986%** search space reduction).

---

## 7. Training-Pair Construction & 8. Hard-Negative Mining
Implemented in `07_training_pairs.py`:
- **Positive Pairs**: All true matches from `train_ground_truth.tsv`.
- **Hard-Negative Mining**:
  - Sampled from top non-matching candidate hits generated by the multi-pass blocking engine.
  - Includes same-street-different-business homonyms, shared acronyms, and single-token overlaps.
- **Ratio**: Maintained a balanced ~1:3 positive-to-hard-negative ratio to train the classifier on fine-grained discriminative boundaries.

---

## 9. Feature Engineering
Implemented in `08_features.py` (44 pairwise dimensions):
1. **Name Metrics**: Exact match, clean exact, Levenshtein ratio, partial ratio, token sort ratio, token set ratio, token Jaccard, 3-gram char Jaccard, 4-gram char Jaccard, length difference, token count difference, legal-stripped token sort ratio.
2. **Address Metrics**: Missing flag, exact match, clean exact, Levenshtein ratio, partial ratio, token sort ratio, token set ratio, token Jaccard, 3-gram char Jaccard, 4-gram char Jaccard, standardized token exact match, street number match, postal zip match.
3. **Country Metrics**: Exact match, missing country indicator.
4. **Cross-Field Interactions**: Harmonic mean of name & address similarities, geometric products, name-sort vs address-jaccard divergence.
5. **Forensic Additions**:
   - `addr_num_mismatch`: Binary penalty when physical door/street numbers directly conflict.
   - `name_acr_match`: Acronym-to-compact name agreement.
   - `name_pfx4_match`: 4-character prefix match.
   - `addr_containment`: Maximum token containment between addresses.

## 11. Validation Split & 12. F0.5 Calculation
- **Entity-Level Validation Split**: Split on unique Source 1 entity IDs (80% train, 20% validation) ensuring zero entity leakage between train and validation folds.
- **Metric Computation**: Macro-averaged across Source 1 entities:
  $$\text{Macro } F_{0.5} = \frac{1}{|S_1|} \sum_{s \in S_1} F_{0.5}(P_s, Y_s)$$

---

## 13. Threshold Optimization
Implemented in `10_validate.py`:
- Swept candidate match thresholds $\tau \in [0.50, 0.95]$.
- Optimal validation Macro $F_{0.5} = \mathbf{0.9523}$ achieved at **$\tau^* = 0.840$**.
- Threshold sensitivity analysis confirmed stability in the $[0.820, 0.860]$ neighborhood ($\pm 0.002$).

---

## 14. Singleton & 15. Multiple-Match Handling
Implemented in `13_entity_decision.py`:
- **Singletons (0 matches)**: When all candidates score below $\tau^* = 0.840$, the entity is output as an empty string `""`.
- **Single / Multiple Matches**: All candidates with probability $p \ge \tau^*$ are sorted by confidence, deduplicated, and formatted as comma-separated IDs (`S2-xxx,S3-yyy`).
- **Safety**: Never defaults to the top-1 candidate if confidence is below threshold.
