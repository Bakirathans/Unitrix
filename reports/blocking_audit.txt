1. CURRENT BLOCKING ARCHITECTURE
--------------------------------------------------
• Multi-Pass Inverted Index with Union Retrieval across 6 key generators:
  1. Compact Alphanumeric Name: {country}|alpha:{alpha} (len >= 4)
  2. Name Character Prefixes:   {country}|pfx6:{pfx6}, {country}|pfx8:{pfx8}
  3. Distinct Informative Tokens:{country}|tok:{token} (len >= 4, no stopwords/digits)
  4. First Two Name Tokens:      {country}|2tok:{t0}_{t1} (bigram prefix)
  5. Domain Name Clean Prefix:   {country}|dom6:{dom_prefix}
  6. Street Number + Word:       {country}|anum:{num}_{street_word}
• Key Indexing Strategy: S2 and S3 are pooled together into a single unified index.
• Bucket Capping: Prunes over-frequent generic keys (MAX_BUCKET_SIZE = 300).
• Production Candidate Selection Restriction:
  - Takes at most 8 items per key bucket (b[:8])
  - Breaks early when candidate count reaches 15 (if len(cand) >= 15: break)
  - Because the last bucket can add up to 8 items to 14 existing items, maximum candidates = 22.
  - Candidates are NOT ranked by similarity before truncation (arbitrary insertion order).

9. DIAGNOSIS OF THE 22-CANDIDATE CEILING
--------------------------------------------------
• Exact Cause: Code implementation in Phase 14 / 15 / 16 candidate generation loop:
  for k in keys:
      b = inverted_index.get(k)
      if b:
          for idx_item in b[:8]:
              cand_noisy_indices.add(idx_item)
          if len(cand_noisy_indices) >= 15:
              break
• Mathematical Proof: If an entity has 14 candidates from earlier keys, and the next key's bucket
  adds 8 distinct new items, the set size becomes 14 + 8 = 22. The loop then checks `len >= 15` and terminates.
  Thus, max candidates is strictly bounded by 14 + 8 = 22.
• Impact: Crucial true matches that appeared after index 8 in a high-quality bucket, or appeared in later
  keys after 15 candidates were arbitrarily accumulated, were completely truncated!

12. ROOT-CAUSE DIAGNOSIS & CONCLUSION
--------------------------------------------------
CONCLUSION: B — Blocking is too aggressive (with top-K / bucket-slicing truncation).
• Pair Recall with current production cap:     58.44% (41.56% of all true matches are LOST before ML inference).
• Theoretical Recall Ceiling (unconstrained):   82.70% (only 17.30% lost when bucket slicing & top-15 cap are removed).
• Key Bottlenecks Identified:
  1. Fixed b[:8] bucket slice + break at >= 15 arbitrarily cuts off true matches.
  2. Inverted index uses arbitrary insertion order (no TF-IDF or key specificity ranking).
  3. Address-only fallback is weak when business names undergo significant alteration.
  4. S3 has lower recall than S2 due to severe token reordering, abbreviations, and noise.
